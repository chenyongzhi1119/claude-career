# STAR 简历描述生成

把用户的一个本地项目提炼成简历可用的 STAR 描述。目标读者是招聘方的简历筛选者和技术面试官。

参数：`$ARGUMENTS`（项目路径，可为空）

## 流程

### 第 1 步：确定项目
- 如果参数给了路径，直接用。
- 如果没给：列出用户项目根目录（如 `~/Projects`）下的项目文件夹，用 AskUserQuestion 让用户选一个。

### 第 2 步：深入分析项目（不要只看 README）
按顺序收集证据：
1. README / 文档：项目定位、功能。
2. 依赖清单（package.json / requirements.txt / pyproject.toml / go.mod 等）：真实技术栈。
3. 目录结构 + 核心源码：架构方式、模块划分、有无测试、有无 CI/部署配置。
4. `git log --oneline | head -50` 和 `git shortlog -sn`：开发历程、迭代重点、用户的贡献占比（多人项目时尤其重要——只能写用户自己做的部分）。
5. 找"简历亮点素材"：性能优化、并发处理、复杂算法、工程化实践（测试/CI/监控）、上线部署痕迹。

### 第 3 步：补齐代码看不出的信息
用 AskUserQuestion 一次性问清（只问代码里确实找不到的）：
- 可量化结果：用户量/请求量/性能数据/star 数/是否上线？
- 项目动机和背景（个人兴趣、课程、工作、外包）？
- 目标岗位是什么（决定强调哪些技术点）？

用户答不上来的量化项，在产出里标注"【建议补充】"，绝不编造数字。

### 第 4 步：产出
输出一份完整交付物，包含：

1. **简历版（bullet points）**：3-5 条，每条动词开头、一行以内、嵌入技术关键词。示例格式：
   > 基于 React + Node.js 独立开发 XXX 系统，采用 YYY 架构解决 ZZZ 问题，支撑【量化结果】。
2. **面试版（STAR 完整叙述）**：Situation / Task / Action / Result 四段，每段 2-4 句，作为面试口述稿。
3. **面试官视角把关**：列出面试官看到这份描述最可能追问的 3 个问题，并提示用户如何准备。
4. **提升建议**：再补做哪 1-2 件低成本的事（如补测试、做压测拿数据、部署上线）能让这段经历更硬。

### 保存
问用户是否保存为 Markdown 文件（默认存到 `~/Documents/resume/项目名-STAR.md`）。

## 原则
- 每一句 Action 都要在代码里有对应证据，经得起面试追问。
- 多人项目只写用户本人的贡献。
- 中文输出，技术名词保留英文。
